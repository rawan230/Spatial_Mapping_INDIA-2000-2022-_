## What Was Done

Step 6 is the pipeline's assembly point. It takes five upstream, independently-produced feature sets — Step 1 fire points, Step 2 NDVI (9 features), Step 3 LST (5 features), Step 4 FLDAS climatic variables (12 features) + ESA CCI/C3S land cover (22 class-fraction features), Step 5a/5b terrain (3 features) + accessibility (3 features) — plus one feature it builds itself (LULC forest fraction), and stacks all of them into one aligned, ML-ready dataset.

| `Integrated_FireRisk_Stack.tif` | **57 bands**, one feature per band (confirmed via `rasterio` band descriptions) |

This is not just a doc claim — it's what the file on disk actually contains.

## How It Was Done

1. **Reuses grid-aligned outputs directly.** Steps 2–5 all already reproject onto Step 2's NDVI grid (3641×3504 px, EPSG:4326, ~0.01°/1km), so Step 6 reads their GeoTIFFs with no further reprojection — cells 7–14 (`print("Loading Step X features...")`) are straight loads, no resampling code.
2. **Builds the one genuinely new feature itself: LULC forest fraction.** Cell 18 reads three years of ESA-CCI/C3S 300m land cover (2001 baseline, 2020 "recent", 2022 "current"), binarizes each to a 13-code forest mask (`FOREST_CODES = {50,60,61,62,70,71,72,80,81,82,90,100,110}` — reconciled with Step 1's own definition on 2026-08-15), and area-averages (`Resampling.average`) each onto the NDVI grid to get a continuous 0–1 fractional-cover value per pixel. Executed-output printout confirms current national means: baseline (2001) 10.2%, recent (2020) 10.5%, current (2022) 10.7%.
3. **Applies the leakage fix at the feature-selection step, not the loading step.** `load_forest_fraction()` still computes all three years (kept as "diagnostic context," per the notebook's own comment) but only `features['forest_frac_baseline']` is assigned into the dict that becomes the exported stack — `forest_recent`/`forest_current` are computed and printed, then simply never added to `features`. This is a clean, minimal, well-isolated fix.
4. **India-masks and flattens** (cell 21/23): applies the India boundary mask, drops any pixel with a NaN in `ndvi_mean` (the validity anchor), stacks all 57 layers into one array, writes the multi-band GeoTIFF with per-band descriptions, and flattens valid pixels into the parquet/CSV-sample pair.
5. **Sanity-checks the result visually** (cell 27): a 57×57 Pearson correlation heatmap across all features (`Feature_Correlation_Matrix.png`, 617 KB), and fire-vs-no-fire boxplot comparisons for the first 12 features (`Fire_vs_NoFire_Feature_Distributions.png`, 167 KB).

## Why It Was Done This Way

- **A dedicated, well-argued markdown cell (cell 19)** documents the leakage rationale in full, not just a code comment: the fire label (`fire_ever`) is a single static pooled binary spanning 2000-11-01 to 2022-12-15 with no per-event year; two of the three dropped features (2020, 2022 LULC) fall *inside* that window; published post-fire land-cover-reclassification literature (ESA-CCI 300m + MODIS burned-area studies) documents burned forest being reclassified to shrubland/agriculture in the *next* LULC epoch — meaning `forest_frac_recent`/`forest_frac_current` could partly encode fire's *outcome*, not a pre-fire condition. The cell also states, concretely, why this mattered: pre-fix, these three features were the model's top-3 Gini-importance features (combined ~0.40 importance) — this was not a peripheral cleanup.
- **`forest_frac_baseline` (2001) was kept, not dropped entirely**, because the label has no per-fire-event year to time-match against, and 2001 is the year closest to a genuine pre-fire condition relative to the bulk of the 2000–2022 fire-occurrence window — an honestly-stated, defensible (not perfect) compromise, explicitly flagged as such.
- **The underlying LULC-loading code for 2020/2022 was deliberately left intact** rather than deleted, preserving the diagnostic printout and making the fix auditable/reversible without re-deriving the reads.
- **The name `forest_frac_baseline` was kept unchanged** (not renamed to `forest_frac`) specifically to avoid a rename ripple into downstream code/docs that already reference it by this exact name — a pragmatic scoping decision.
- **Downstream impact was explicitly flagged, not silently left implicit**: both the notebook's closing cell and the README state that Step 7 and the CDR-PINN work still referenced the dropped columns as of Step 6's fix commit and would need separate updates — this is disclosed scope-boundary honesty rather than a hidden gap. (This audit independently verified that Step 7's downstream retrain has since happened — `Integrated_Analysis/Model_Outputs/` now contains `Model_Comparison_SpatialBlockCV.csv` and `rf_hp_search_result.json`, both dated after the leakage-fix commit, and the fix commit's own message reports a re-trained RF AUC of 0.9687 post-fix, later tuned to 0.9698 — see the Completeness Audit below for the one loose end this created.)

## Impact on Spatial Fire Mapping in India

Step 6 is what turns five independently-timed, independently-produced GeoTIFF stacks into a single per-pixel, model-ready table covering essentially the entire forested and non-forested landmass of India at ~1km resolution (4.16M valid pixels). Its two direct downstream consequences:

1. **It is the only place a spatial fire-susceptibility model can be trained on this project's full feature set at all** — Step 7's Random Forest/MaxEnt and Step 8's CDR-PINN both read this parquet/stack directly; neither model does its own alignment.
2. **The leakage fix materially changes what "explains" fire risk in every downstream model.** Because the dropped features were the top-3 Gini-importance features pre-fix, removing them forces every downstream model to re-derive its explanation of spatial fire risk from features that cannot causally postdate the fires they're meant to predict — a correctness-over-convenience trade that directly affects the credibility of any map or variable-importance claim built on top of this step. The retrain confirms the fix didn't just remove noise: `forest_frac_baseline` alone still lands as the single top Gini-importance feature in the post-fix, hyperparameter-tuned model (importance 0.2066, per the `484015d` commit message), i.e. genuine forest-fraction signal survives the fix; only the temporally-invalid *snapshots* of it were removed.

## Comparison with Biswas et al. (2025)

- **Feature richness:** the README explicitly states parity and extension — "this is the first run in which the trained feature table genuinely covers all 15 of Biswas et al. (2025)'s real predictor variables... previously only 9 of 15 were present" — and separately notes the leakage fix removed only *redundant* forest-fraction snapshots (60→57 bands), not a distinct predictor category, so 15/15 parity is unaffected by the fix. This comparison is made explicitly, correctly, and repeatedly in both the notebook's closing markdown cell and the README.
- **Spatial resolution:** Step 6's own README and notebook do **not** state a resolution comparison anywhere — no mention of 0.25° or a finer-resolution claim appears in `README.md` or the notebook JSON. The comparison exists, but only in the separate cross-step reference file `PIPELINE_SUMMARY.md` (last updated 2026-08-20, i.e. *before* the leakage fix, and not part of Step 6's own documentation set), which makes a detailed, well-sourced case: Biswas et al.'s common working grid is 0.25° (~27km, ~730 km²/pixel, quoting their own paper's stated resolution), versus this pipeline's 1km grid (~1 km²/pixel) — a ~27× linear / ~730× areal resolution advantage for NDVI/LST/LULC/fire-label sources, and a smaller but still real ~2.5–6× advantage for the bilinearly-interpolated FLDAS climatic features (native ~11km/0.1°).
- **Net assessment:** feature-count parity is well-documented at the Step 6 level; the resolution advantage is well-argued but lives one level up, outside this step's own README/notebook — see Gap 3 below.
